가재코드를
“실행기”가 아니라
작업 시스템으로 쓰기

중급 단계의 차이는 에이전트에게 더 긴 프롬프트를 주는 데 있지 않습니다. 변경 전에는 불확실성을 줄이고, 변경 중에는 범위를 통제하며, 변경 후에는 사람이 검토 가능한 증거를 남기는 데 있습니다.

작성: Gajae-Code Guide Desk읽는 시간: 약 12분 · 대상: 웹·iOS·Android·프로토타입 개발자
목차 펼치기가재코드의 자리작업 루프명령어 레퍼런스실전 시나리오모델·세션 운영프롬프트 템플릿

가재코드는 특정 에디터나 에이전트를 대체하는 숨은 확장 기능이 아니라, 선택한 저장소·워크트리 곁에서 실행하는 독립적인 작업 레이어다.

1. 가재코드의 자리: 모델과 저장소 사이

가재코드는 모델을 고르는 도구이기도 하고 터미널 에이전트이기도 하지만, 실제 강점은 그 둘 사이에 작업 규율을 놓는 데 있습니다. “코드 만들어줘”라는 한 번의 요청을, 요구사항·계획·실행·검증이라는 이어지는 기록으로 바꿉니다.

레이어가재코드가 맡는 일개발자가 끝까지 맡는 일
의도질문을 통해 요구와 비목표를 문서화제품 판단, 우선순위, 승인
계획영향 범위와 검증 순서를 드러냄계획의 트레이드오프 결정
실행도구 호출, 코드 변경, 목표 추적위험한 변경의 경계 설정
검증테스트·diff·근거를 수집릴리스/머지의 최종 판단
“좋은 에이전트 세션은 답변이 길어서가 아니라, 다음 사람이 왜 이 변경을 믿어도 되는지 알 수 있어서 좋다.”
중급자 기준에이전트가 파일을 고쳤다는 사실은 완료 증거가 아닙니다. 기대 동작, 실행한 검증, 남은 리스크가 함께 있어야 완료입니다.

2. 매번 재사용하는 작업 루프

모든 작업에 네 가지 스킬을 모두 쓸 필요는 없습니다. 핵심은 작업의 불확실성과 위험에 맞춰 최소한의 게이트를 두는 것입니다.

변경 전: 질문 → 계획 → 승인

1

작업을 분류한다

단일 파일의 명확한 버그라면 바로 실행합니다. 제품 요구가 모호하거나 데이터·권한·여러 패키지가 얽히면 deep-interview부터 시작합니다.

2

완료 조건을 문장으로 만든다

“온보딩 개선” 대신 “첫 실행 사용자에게만 3단계 노출, 건너뛰기 가능, 완료 이벤트 기록, VoiceOver 통과”처럼 관찰 가능한 조건을 남깁니다.

3

계획에 승인 지점을 둔다

ralplan으로 파일·데이터 변경·테스트·롤백을 검토한 뒤, 구현 시작을 명시적으로 승인합니다. 계획은 구현 허가가 아닙니다.

gjc --tmux --worktree profile-notifications

"알림 설정을 추가하고 싶다. 구현은 시작하지 말고,
현재 설정 저장 방식·플랫폼별 권한·기존 분석 이벤트를 조사한 뒤
결정이 필요한 질문과 완료 조건을 먼저 정리해줘."

/skill:ralplan
"합의된 완료 조건으로 영향 파일, 마이그레이션, 테스트, 롤백까지 포함한 계획을 작성해줘."

변경 후: 증거 → 검토 → 다음 세션

완료 보고는 “끝났습니다”가 아니라 다음 네 가지를 가진 짧은 릴리스 노트여야 합니다.

  • 변경: 사용자에게 달라진 동작과 핵심 파일
  • 검증: 실제 실행한 테스트·빌드·수동 확인
  • 제한: 실행하지 못한 테스트나 환경 제약
  • 후속: 배포 후 관찰할 지표 또는 별도 작업

💡 ultragoal은 언제 쓰나요?

여러 세션에 걸치거나, 중간에 리뷰·수정·재검증이 필요한 작업에 사용합니다. 작은 수정에 과도한 목표 관리가 필요하진 않지만, “누가 무엇을 어떤 근거로 끝냈는가”가 중요한 프로젝트라면 큰 차이를 만듭니다.

3. 중급자가 자주 여는 명령어 레퍼런스

가재코드는 대화형 화면 안의 슬래시 워크플로와, 셸에서 호출하는 CLI를 함께 씁니다. 아래는 일상적으로 반복되는 명령만 추렸습니다.

명령언제 쓰나중급자 메모
gjc현재 프로젝트에서 대화형 세션 시작시작 요청에 “먼저 조사, 수정 전 계획”을 넣으면 섣부른 변경을 줄인다.
gjc --tmux오래 가는 작업세션이 끊겨도 tmux 맥락을 유지하기 좋다.
gjc --tmux --worktree 이름위험하거나 리뷰 가능한 변경현재 브랜치를 보호하는 가장 쉬운 기본값이다.
gjc -p "…"한 번 분석하고 종료CI 보조, 코드베이스 조사, PR 전 체크에 알맞다.
gjc --continue "…"마지막 작업 이어가기새 맥락을 재설명하기보다 변경된 조건만 덧붙인다.
gjc skills list번들 워크플로 확인기본 스킬을 가정하지 말고 설치·내용을 먼저 확인한다.
gjc skills read ralplan스킬의 정확한 계약 확인팀의 작업 규칙과 충돌하는지 읽어본다.
gjc --list-models현재 인증된 모델 확인실패가 모델 미지원/인증 때문인지 초기에 구별한다.

기본 스킬 설치와 확인

# 기본 워크플로 파일의 상태만 점검
gjc setup defaults --check

# 누락된 기본 워크플로 설치 (기존 로컬 파일은 보존)
gjc setup defaults

# 한 번 처리하고 결과만 출력
gjc -p "현재 diff를 검토해. 고쳐야 할 문제만 심각도 순으로 알려줘."
명령어보다 중요한 운영 규칙--worktree는 파일 경로가 아니라 가재코드가 만들 형제 워크트리의 브랜치형 이름을 받습니다. 이미 만든 워크트리라면 그 디렉터리로 이동한 뒤 gjc를 실행하세요.

4. 실전 시나리오: 속도와 신뢰를 같이 얻는 법

시나리오 A — 결제 오류를 고치는 웹앱 개발자

결제 관련 이슈는 “버그가 보이는 화면”만 바꾸면 재발하기 쉽습니다. 웹훅, 멱등성, 상태 전이, 관찰 지표를 먼저 확인해야 합니다.

gjc --tmux --worktree checkout-retry

"간헐적인 중복 결제 보고를 조사해줘. 먼저 결제 생성, 웹훅 처리,
재시도 정책, 주문 상태 전이를 읽고 재현 가설을 순위별로 제시해줘.
코드는 아직 바꾸지 마. 각 가설의 확인 방법도 적어줘."

이 요청의 좋은 점은 수정 대상 대신 조사 대상과 가설 검증 방식을 준다는 것입니다. 확인된 원인이 생긴 뒤에만 계획과 변경으로 넘어갑니다.

시나리오 B — iOS/Android의 상태 복원 기능

모바일 기능은 화면 하나보다 앱 수명주기와 데이터 경계가 어렵습니다. 플랫폼별 구현은 달라도 계획의 질문은 거의 같습니다.

질문iOS 관점Android 관점
언제 복원?scene/app lifecycle, 딥링크process death, saved state, task 재개
무엇을 보존?Navigation path, draft, 로그인 상태back stack, ViewModel state, draft
어떻게 검증?UI test, 실제 기기, 접근성instrumentation test, 회전·백그라운드 전환
gjc --tmux --worktree draft-recovery
"작성 중인 초안을 앱 재시작 뒤 복원하는 기능을 설계해줘.
저장 주기, 민감 데이터, 계정 전환, 충돌, 앱 강제 종료를 포함해
질문부터 정리하고 승인 전 계획을 만들어줘."

시나리오 C — 프로토타입을 제품으로 올리는 바이브코더

프로토타입 단계에서 가재코드는 속도를 늦추는 관료제가 아니라, 만들지 않을 것을 빨리 결정하는 장치입니다. MVP는 기능 목록보다 비목표 목록이 더 중요합니다.

gjc --tmux --worktree customer-insights-mvp
"고객 인터뷰 녹취를 요약하는 MVP를 3일 안에 데모해야 해.
필수 사용자 흐름 하나, 데모 성공 기준, 비목표, 개인정보 위험,
예상 비용을 질문해서 한 페이지 명세로 정리해줘.
명세를 승인하기 전에는 구현하지 마."

5. 모델·세션 운영: 좋은 모델보다 좋은 분리

깊은 모델 하나에 모든 역할을 몰아주기보다, 작업 성격을 구분하는 편이 대개 효과적입니다. 단, 모델 라우팅은 인증된 공급자·계정에서 실제로 쓸 수 있는 모델을 기준으로 정해야 합니다.

작업운영 방법예시
정찰·요약빠른 모델 또는 짧은 print 세션gjc -p "src 구조를…"
설계·트레이드오프충분한 추론 예산 + 계획 게이트gjc --mpreset codex-medium
위험한 구현워크트리 + 대화형 세션 + 테스트gjc --tmux --worktree …
재검토새 세션/다른 관점으로 diff만 검토gjc -p "현재 diff를…"
주의: 이어가기와 독립 검토는 목적이 다릅니다.--continue는 기존 맥락과 결정을 이어가는 데 좋습니다. 반대로 이미 작성한 코드를 비판적으로 보고 싶다면, 새 print 세션에서 spec·diff·테스트 결과만 주고 검토하게 하세요.

세션을 작은 기록으로 관리하기

  • 시작 메시지에 목적·제약·완료 조건을 넣는다.
  • 중간에 제품 결정이 바뀌면 “이전 계획의 어떤 전제가 바뀌었는지”를 명시한다.
  • 세션이 길어지면 gjc --continue로 맥락을 잇되, 핵심 결정은 짧게 다시 요약한다.
  • 공유가 필요하면 세션 HTML 내보내기를 이용하되, 민감 정보가 포함되지 않았는지 먼저 검토한다.

6. 흔한 실패 패턴과 교정법

실패 패턴왜 실패하나교정 문장
“이 기능 만들어줘”범위·비목표·테스트가 없어 에이전트가 추측한다.“먼저 결정이 필요한 항목과 완료 조건을 질문해줘.”
계획을 받은 즉시 구현데이터 마이그레이션·권한·롤백을 사람이 확인하지 않는다.“계획은 승인 대기 상태로 두고, 위험 항목을 먼저 표시해줘.”
메인 브랜치에서 긴 작업실험과 긴급 수정이 서로 방해한다.“--worktree로 별도 작업 공간에서 시작하자.”
“테스트해줘”로 끝냄어떤 테스트를 했고 못 했는지 알 수 없다.“실행 명령, 결과, 미실행 사유, 남은 리스크로 보고해줘.”
병렬 작업을 많이 띄움의존성이 있는 변경이 충돌하고 통합 비용이 늘어난다.“독립적인 조사와 테스트 보강만 병렬로 나눠줘.”

7. 복사해서 쓰는 중급자 프롬프트 템플릿

좋은 프롬프트의 핵심은 상세한 구현 지시가 아니라, 의사결정 경계와 확인 방법을 명시하는 것입니다.

목적: [사용자/비즈니스 관점에서 달성할 결과]

현재 상황: [문제, 관련 기능, 관찰한 증상]
제약: [건드리면 안 되는 것, 호환성, 일정, 보안/비용 조건]
완료 조건:
- [관찰 가능한 동작 1]
- [관찰 가능한 동작 2]
- [필수 테스트 또는 수동 검증]

진행 방식:
1) 먼저 관련 코드와 테스트를 조사해 요약한다.
2) 불명확한 부분은 질문하고, 가정은 분리해서 적는다.
3) 구현 전 영향 파일·리스크·검증법이 있는 계획을 제시한다.
4) 내가 승인한 뒤에만 변경한다.
5) 완료 시 변경, 검증 결과, 미실행 항목, 남은 리스크를 보고한다.
  • 이 작업의 “하지 않을 것”을 한 줄이라도 썼는가?
  • 정상 흐름뿐 아니라 실패·취소·재시도 상태를 언급했는가?
  • 테스트가 없을 때 사람이 확인할 방법을 적었는가?
  • 권한, 개인정보, 결제, 삭제, 배포처럼 되돌리기 어려운 지점이 있는가?

마무리: 빠른 것은 빨리, 중요한 것은 분명하게

가재코드의 워크플로는 모든 작업을 무겁게 만들자는 제안이 아닙니다. 작은 수정은 짧게 끝내고, 애매하거나 위험한 변경만 인터뷰·계획·증거로 다루자는 제안입니다. 익숙해지면 에이전트에게 맡기는 범위가 커질수록 오히려 통제감도 커집니다.

다음 실험

이번 주 작업 하나를 골라 gjc --tmux --worktree 실험이름으로 시작해 보세요. 구현 요청 전에 “계획을 승인 대기 상태로 작성해줘”라고 말하고, 완료 보고에 테스트 결과와 남은 리스크를 요구하면 됩니다.
