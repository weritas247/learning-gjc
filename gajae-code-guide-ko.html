Gajae-Code / gjc

의도를 정리하고,
검증되는 코드로.

가재코드는 단순히 코드를 생성하는 도구가 아닙니다. 요구사항을 묻고, 계획을 검토하고, 작업의 완료 근거를 남기도록 설계된 코딩 에이전트 러너입니다.

자주 쓰는 명령어 보기 ↓내 직군 사례 보기

무엇인가요?선택한 저장소 옆에서 실행하는 외부 코딩 에이전트입니다.

언제 쓰나요?요구사항이 모호하거나, 큰 변경을 안전하게 추진할 때 좋습니다.

핵심 원칙계획 없이 수정하지 않고, 검증 없이 완료하지 않습니다.

기본 명령gjc를 프로젝트 폴더에서 실행하세요.

The method

코드를 바꾸기 전에, 일의 모양을 만듭니다.

작은 버그는 바로 처리해도 됩니다. 하지만 불명확하거나 영향 범위가 큰 작업은 아래 흐름을 거치면 결과의 품질과 설명 가능성이 좋아집니다.

deep-interview

모호한 요청을 질문으로 풀어 명확한 요구사항과 완료 조건으로 바꿉니다.

ralplan

수정 전에 접근법·영향 범위·검증법을 검토하고 합의 가능한 계획을 만듭니다.

ultragoal

큰 작업을 목표로 나누고, 실행·수정·테스트·증거를 지속적으로 기록합니다.

team

독립적인 하위 작업만 tmux 워커에게 병렬로 맡겨 시간을 줄입니다.

가장 중요한 구분: 가재코드는 Codex/Claude Code의 숨은 플러그인이 아닙니다. 기존 도구를 덮어쓰지 않고, 같은 프로젝트 폴더 또는 별도 워크트리에서 함께 실행하는 독립 워크플로입니다.
Command cookbook

많이 쓰는 명령어, 상황별로 고르기

왼쪽 상황을 눌러 실제 입력 예시를 확인하세요. 명령은 모두 프로젝트 루트에서 실행하는 것을 기준으로 합니다.

대화형 세션 열기

현재 폴더를 작업 대상으로 삼아 에이전트와 대화합니다. 첫 실행이라면 기본 워크플로도 설치하세요.

cd ~/dev/my-project
gjc setup defaults
gjc

이렇게 말해보세요. “이 저장소의 구조와 테스트 방법을 먼저 설명한 뒤, 내가 고칠 만한 작은 이슈 3개를 우선순위로 제안해줘.”

질문 하나를 처리하고 종료하기

-p는 자동화, CI 보조, 빠른 분석처럼 대화형 화면이 필요 없을 때 씁니다.

gjc -p "src의 인증 흐름을 요약하고 위험한 예외 처리를 찾아줘"

# 이미지 또는 문서를 함께 전달
gjc -p @bug-screenshot.png @requirements.md "재현 경로와 수정안을 정리해줘"

좋은 사례. PR을 열기 전에 “현재 변경분을 검토하고, 빠진 테스트만 목록으로 알려줘”라고 요청합니다.

요구사항과 계획을 먼저 다듬기

구현이 아니라 생각의 품질이 병목일 때 사용하는 기본 스킬입니다.

# 세션 안에서 슬래시 명령으로 사용
/skill:deep-interview
"팀 초대 기능을 만들고 싶어. 무엇을 먼저 정해야 할까?"

/skill:ralplan
"승인된 요구사항 기준으로 구현 계획과 검증 항목을 만들어줘."

# 설치된 기본 스킬 살펴보기
gjc skills list
gjc skills read ralplan

언제 유용한가요? “로그인 기능 추가”처럼 범위가 넓은 말보다, 권한·오류·UI·테스트 기준을 먼저 확정해야 할 때입니다.

tmux와 별도 워크트리로 안전하게

오래 걸리는 작업은 tmux에서 유지하고, 위험하거나 리뷰할 변경은 분리된 Git 워크트리에서 수행합니다.

# tmux 기반 리더 세션
gjc --tmux

# my-feature라는 형제 워크트리를 만들고 그곳에서 시작
gjc --tmux --worktree my-feature

사례. 운영 중인 웹앱의 결제 모듈을 바꿀 때, 현재 브랜치를 더럽히지 않고 my-feature 워크트리에서 계획·수정·테스트를 모두 진행합니다.

사용 가능한 모델과 설정 보기

인증한 공급자에 따라 선택 가능한 모델이 달라집니다. 대화형 세션 안에서는 /login <provider>로 인증할 수 있습니다.

gjc --version
gjc --list-models
gjc --model opus "복잡한 리팩터링 계획을 검토해줘"
gjc --mpreset codex-medium

기본 원칙. 평소에는 균형형 모델, 설계·보안·복잡한 디버깅에는 더 깊은 추론 모델을 쓰고 결과는 테스트로 확인하세요.

이전 작업을 이어서 하기

세션을 남기는 방식이므로, 어제의 맥락을 이어서 후속 작업과 검증을 할 수 있습니다.

# 마지막 세션 이어가기
gjc --continue "방금 만든 계획의 2단계를 구현해줘"

# 세션 목록/관리 기능 살펴보기
gjc session --help

# 세션을 HTML로 내보내기
gjc --export ~/.gjc/agent/sessions/.../session.jsonl

사례. 월요일에 합의한 계획을 금요일에 이어서 실행할 때, 새로 설명하기보다 기존 세션을 재개한 뒤 변경 사항만 알려줍니다.

Four ways to work

직군별로 보면 사용법이 더 선명해집니다.

아래 페르소나는 가재코드를 “무엇을 시킬 수 있나”가 아니라 “어떤 순서로 협업하면 좋은가”로 보여줍니다.

🌐

서연

React · Next.js 웹앱 개발자

회원가입 전환율을 올려야 하지만, UX·분석 이벤트·서버 검증이 뒤섞여 있습니다.

가재코드를 쓰는 방식

  • 먼저 deep-interview로 성공 지표, 실패 상태, 기존 분석 이벤트를 확인합니다.
  • ralplan으로 프론트·API·DB 마이그레이션·E2E 테스트 순서를 검토합니다.
  • 변경은 워크트리에서 진행하고, 마지막에 접근성·모바일 화면·회귀 테스트를 증거로 남깁니다.
gjc --tmux --worktree signup-conversion

"회원가입 전환율 개선을 검토해줘. 먼저 현재 플로우, 이벤트,
서버 유효성 검사를 조사하고, 영향 범위와 측정 기준을 질문해줘."

# 요구사항이 합의된 뒤
/skill:ralplan
"A/B 실험 없이 안전하게 배포할 구현 계획과 테스트 체크리스트를 만들어줘."
🍎

민준

SwiftUI iPhone 앱 개발자

새 온보딩을 만들지만, 접근성·상태 복원·다양한 화면 크기를 놓치고 싶지 않습니다.

가재코드를 쓰는 방식

  • 요구 인터뷰에서 최소 지원 iOS 버전, 로그인 상태, VoiceOver 동작, 분석 이벤트를 명시합니다.
  • 계획 단계에서 화면 상태 모델과 네트워크 실패 시나리오를 먼저 나눕니다.
  • 구현 요청에는 Preview, UI 테스트, 실제 기기 확인 항목을 완료 조건으로 넣습니다.
gjc --tmux --worktree onboarding-ios

"SwiftUI 온보딩 3단계를 추가하려고 해. 상태 복원, 다크 모드,
Dynamic Type, VoiceOver, 로그인 완료 후의 전환까지 포함해
먼저 질문하고 설계안을 만들어줘."
🤖

지수

Kotlin · Compose Android 개발자

오프라인에서도 동작하는 피드 기능을 추가하고, API·로컬 캐시·동기화를 함께 다뤄야 합니다.

가재코드를 쓰는 방식

  • 먼저 데이터 소스, 캐시 만료, 충돌 해결, 네트워크 상태별 UX를 질문으로 확정합니다.
  • 계획에서 Repository 계층·Room 마이그레이션·WorkManager 작업·Compose UI 테스트를 분리합니다.
  • 독립적인 조사와 테스트 보강만 team으로 병렬화합니다.
gjc --tmux --worktree offline-feed

"Compose 피드에 오프라인 캐시를 넣고 싶어. 현재 Repository와
동기화 흐름을 조사한 뒤, 데이터 일관성·마이그레이션·테스트 리스크를
포함한 계획을 제안해줘. 코드는 아직 수정하지 마."
⚡

도윤

바이브코딩 초고수 · 제품 프로토타이퍼

아이디어를 빠르게 제품으로 옮기지만, 빠른 속도가 빚과 보안 누락으로 이어지지 않게 합니다.

가재코드를 쓰는 방식

  • 한 문장 아이디어를 deep-interview로 MVP 범위, 비목표, 데모 성공 기준까지 압축합니다.
  • 계획을 승인한 뒤에만 ultragoal로 UI·데이터·배포 준비를 쪼갭니다.
  • 마지막에는 “보이는 데모”와 “재현 가능한 검증”을 따로 요청합니다.
gjc --tmux --worktree meal-planner-mvp

"냉장고 사진으로 3일 식단을 제안하는 MVP를 만들고 싶어.
48시간 데모 기준으로 반드시 필요한 기능, 절대 만들지 않을 기능,
개인정보·비용 리스크를 질문해서 한 장짜리 명세로 정리해줘."

# 승인 후
gjc ultragoal create-goals --brief-file .gjc/specs/meal-planner.md
Your first day

첫날에는 이 정도면 충분합니다.

처음부터 모든 기능을 쓰기보다, 한 번의 작은 작업을 계획부터 검증까지 완주해보세요.

01

프로젝트에서 시작

cd 프로젝트 뒤 gjc를 실행합니다. 어떤 저장소를 대상으로 하는지가 가장 중요합니다.

02

요청에 완료 조건을 넣기

“수정해줘” 대신 대상 파일, 기대 동작, 테스트 기준, 건드리면 안 되는 범위를 함께 말합니다.

03

변경 전 계획 확인

작업이 크거나 애매하면 /skill:ralplan을 먼저 요청하고, 계획에 동의한 뒤 실행합니다.

04

별도 워크트리 쓰기

현재 작업을 보호해야 한다면 gjc --tmux --worktree 이름으로 분리합니다.

05

테스트 결과를 요구

“어떤 테스트를 실행했고, 무엇이 통과/실패했는지”를 완료 보고에 반드시 포함시키세요.

06

최종 판단은 내가

가재코드는 베타 도구입니다. 특히 인증, 결제, 삭제, 배포 변경은 diff와 테스트를 직접 검토합니다.
